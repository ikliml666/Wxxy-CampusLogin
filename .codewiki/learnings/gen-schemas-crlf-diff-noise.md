## 现象

一次 `tauri android build` / `gradle` 构建后，`git status` 对以下生成物报出全文件 diff，肉眼 `git diff` 看似“内容没变，仅整文件被重写”：

- `android/src-tauri/gen/schemas/acl-manifests.json`（源码 1| 起，单行紧凑 JSON）
- `android/src-tauri/gen/schemas/android-schema.json`（源码 1| 起，格式化 JSON）
- `android/plugins/foreground-service/permissions/default.toml`（源码 1| 起）
- `android/plugins/foreground-service/permissions/autogenerated/reference.md`（源码 1| 起）

这些文件都是构建 / 代码生成阶段再生的产物，不属于手改来源。

## 根因

构建或生成过程把行尾由仓库标准的 `\n`（LF）重写为 `\r\n`（CRLF），属生成阶段的行尾噪音。当前工作区若处于该状态，`git ls-files --eol` 对上述生成物报 `i/lf w/crlf`——即仓库索引内是 LF（`i/lf`），而工作区文件被写成 CRLF（`w/crlf`）。

## 解决

提交前对这类生成物执行 `git checkout -- <path>` 还原工作区版本（丢弃 CRLF 重写）；若确属内容变更（见下），才正常 `git add` 并提交。

## 教训

`gen/` 与 `plugins/*/permissions/autogenerated/` 下的自动生成物在构建后必然带行尾噪音，**提交前先还原**，不要把这些 diff 混进业务提交（见 [[android-generated-project-discipline]]）。

**区分内容变更与行尾噪音**：插件 ACL / 命令面真正变更时，schema 文件的**内容**变化（新增 / 删除权限项）是应该提交的。以当前代码为准核对：

- `acl-manifests.json` 中 `campus-monitor-service` 对象的 `default_permission.permissions` 含 12 项：`allow-startMonitor`、`allow-stopMonitor`、`allow-updateNotification`、`allow-setBootAutostart`、`allow-isBootAutostartEnabled`、`allow-installApk`、`allow-beginProbeWindow`、`allow-endProbeWindow`、`allow-getPowerState`、`allow-getBatteryOptimizationInfo`、`allow-requestIgnoreBatteryOptimizations`、`allow-openVendorBatterySettings`。
- `android/plugins/foreground-service/permissions/default.toml` 的 `[default].permissions` 数组（源码 7| 起至 19|）逐行列出这相同的 12 项。
- `android/plugins/foreground-service/permissions/autogenerated/reference.md` 从 1| 起描述默认权限，并在 30| 起以表格列出 `campus-monitor-service:allow-*` / `:deny-*` 各标识符（如 33| `campus-monitor-service:allow-installApk`、111| `campus-monitor-service:allow-startMonitor`、137| `campus-monitor-service:allow-stopMonitor` 等）。
- `android-schema.json` 的 `definitions.Identifier.oneOf` 中亦含 `campus-monitor-service:default`（源码 407| 起 `const`）及其各 `allow-*` / `deny-*` 常量（413|–484|）。

若上述权限集合与上次提交一致，却出现整文件 diff，那仅是行尾被重写，属噪音，应 `git checkout --` 丢弃。

**判据与陷阱**：本机 `core.autocrlf=true`（Git for Windows 常见系统配置）时，工作区取出 / 写入会做 CRLF⇄LF 转换，`git status` 可能因规范化而显示“干净”——这不等于“构建没动过这些文件”。确认须看 `git ls-files --eol`：`w/crlf` 即工作区被写成 CRLF；换机器、或改为 `core.eol=lf`、或给生成物在 `.gitattributes` 加 `-text` 属性后，同一现象就会以整文件 diff 的形式暴露出来。
