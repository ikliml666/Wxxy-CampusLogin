## Overview

`release-and-changelog-archive` 是 Wxxy-CampusLogin 的**纯文档归档层**，不含任何可执行代码、类型定义或函数：目录里只有 Markdown 文本与一行校验和，被构建链完全忽略，只服务于"追溯某个版本为什么改、改了什么、怎么验证的"。

它由三个互不重叠的子集构成：

1. **`changelogs/` —— 按版本文件维护的开发者变更日志**。每个文件对应一个大版本（`CHANGELOG_v2.3.6.md` … `CHANGELOG_v2.4.1.md`），条目按 `- **YYYY-MM-DD 标题** — 模块` 开头，正文强制包含"根因 / 做法 / 验证"三段式证据。这条约定在 `changelogs/CHANGELOG_v2.3.8.md:32` 中被正式确立：原单文件 `CHANGELOG.md`（73 条全部堆在 `[Unreleased]`）按日期切分到版本文件，此后新内容一律写入 `CHANGELOG_v<当前版本+1>.md`，发布后封版、新内容顺延下一版，取消快照步骤。`changelogs/_audit-fix-plan.md:106` 即按该规则预留了 `changelogs/CHANGELOG_v2.4.2.md` 的追加位。

2. **`release/` —— 面向用户的分发物**。`RELEASE_NOTES_v2.3.3.md` 到 `RELEASE_NOTES_v2.4.1.md` 是直接贴进 GitHub Release 正文的用户语言文档（导读段 + emoji 主题节 + 升级说明），加一个安装包校验和文件。这些是"从 changelog 提炼、按用户可见性取舍"的派生物，构建脚本/文档类改动不进 release（见 `changelogs/CHANGELOG_v2.3.7.md:13-14`、`changelogs/CHANGELOG_v2.4.0.md:262`）。

3. **`changelogs/_audit-fix-*.md` —— 审计派单与回执**。`_audit-fix-plan.md` 是一次全量审计（三路审计 + 双复审 + 主 agent 终审，54 条原始发现中 49 条成立）的唯一需求来源，按 A/B/C/D 四组分派给子代理；`_audit-fix-report-A.md` ~ `-D.md` 是各组逐条"项号 → 文件:行号 → 怎么改 → 验证结果"的回执。

关键前提：**`changelogs/` 与 `release/` 都在 `.gitignore` 中，仅本地留存、不入 git**（见 `changelogs/CHANGELOG_v2.3.8.md:32` 的"不再维护统一的 CHANGELOG.md"、`changelogs/CHANGELOG_v2.4.0.md:262` 的"release/ 目录被 .gitignore:7 忽略，与历代 release notes 一致仅本地维护"）。因此本模块在仓库克隆中**通常为空**，它的存在依赖于维护者本机的历史文件；任何"新克隆仓库缺 changelog"的现象都是设计结果而非缺陷。

## Key Components

本模块无函数、无 struct、无常量。组件单位是**归档文件本身**，每个文件的行号锚点与内容职责如下。

- **根因**：带日志时间戳与复现证据，例如 `:9-17` 记录 `2026-09-11 21:18:28.911` 的 `尝试重载 WebView: 浏览器进程退出（WebView 已整体失效）(kind=0)` 与 `Crashpad/temp/edge_shutdown_crash.txt` 同刻落盘，并说明"原恢复动作 `window.eval("window.location.reload()")` 返回成功但页面不恢复"；
- **修复**：给出改动落点与函数名，如 `:18-21` 的 `handle_process_failed` 按 `BROWSER_PROCESS_EXITED` / `RENDER/FRAME_RENDER_PROCESS_EXITED` 分流、新增 `attempt_app_restart` 与 `webview_restart_guard` 落盘限流（10 分钟窗口最多 2 次）；
- **诊断链**：记录为定位补的可观测性，如 `:22-25` 补读 `ICoreWebView2ProcessFailedEventArgs2` 的 `Reason` / `ExitCode`；
- **验证**：命令 + 用例数，如 `:26-27` 的 `cargo check` 通过、`cargo test` 255 + 1 全绿及新增两个单测名。

```text
│             _audit-fix-report-A/B/C/D.md（逐条 项号→文件:行号→改法→验证 + 偏离/未做）    │
└──────────────────────────────────────────────────────────────────────────────────────────┘
        │ 写入约定：新条目 → CHANGELOG_v<当前版本+1>.md；vX 封版 → RELEASE_NOTES_vX.md
        ▼
   make-release.ps1 收集 release/ ├── release notes ├── 安装包改名 + .sha256 ├── APK
```

## Data Flow

归档层没有运行时数据流，只有**写入链**与**消费链**两条人工流程。

**写入链（开发期 → 发布期）**

1. 一次改动完成并验证后，按其用户可见性决定去向：代码/配置/构建改动写进当前开发版本的 `changelogs/CHANGELOG_v<当前版本+1>.md`；构建脚本与文档类改动只留 changelog、不进 release（`changelogs/CHANGELOG_v2.3.7.md:13-14` 明确"构建脚本/文档类不进 release"）。
2. 条目撰写强制四段式（根因 / 做法 / 验证，必要时加诊断链与遗留），证据必须可复核：日志时间戳、文件名、函数名、测试用例名与通过数。范例见 `changelogs/CHANGELOG_v2.3.6.md:8-27`。失败与未验证必须如实写进"遗留"，如 `:78-79`"需真机在 WiFi+流量同开场景复验；本机无设备/无 adb，仅做到交叉编译与 Kotlin 编译级验证"。
3. 版本号升级成为独立条目，并**连带维护 release 文稿**：`changelogs/CHANGELOG_v2.3.7.md:8-16` 记录附录 H 清单 15 处版本号、`version.json` 补 `notes`（双端关于弹窗/更新弹窗共用同一 `### 标题` / `- 列表` 渲染契约）、并新写 `release/RELEASE_NOTES_v2.3.7.md`（内容取自 v2.3.6 发布后的全部 `[Unreleased]` 条目并按用户可见性取舍）。
4. 发布期：`make-release.ps1` 包装 `tauri-app/build.ps1`，把安装包统一改名为 updater 硬编码的 `Wxxy-CampusLogin_{ver}_x64-setup.exe`、生成 `.sha256`、把 APK 与 `RELEASE_NOTES_v{ver}.md` 一并收进 `release/`，结尾打印 `gh release upload` 命令（`changelogs/CHANGELOG_v2.3.7.md:369-376`）。同日该脚本一度误入库（commit 616c430）后撤销（f054255），维持"仅本地保留"约定（`:25`、`:376`）。
5. 发布后 vX 封版：该版本文件不再追加，新内容顺延写入下一版文件（`changelogs/CHANGELOG_v2.3.8.md:32`）。封版无额外快照步骤。

**消费链（三个下游）**

- **用户**：`release/RELEASE_NOTES_v*.md` 作为 GitHub Release 正文发布；`version.json` 的 `notes` 字段从同批内容提炼，被双端更新弹窗渲染（`changelogs/CHANGELOG_v2.3.7.md:11-12`、`:10` 的"更新弹窗排版重做…本版起更新说明随版本号一起维护"）。v2.3.6 曾因漏维护说明字段导致更新内容空白（`release/RELEASE_NOTES_v2.3.7.md:7`、`:10`）。
- **审计修复子代理**：`changelogs/_audit-fix-plan.md` 是唯一需求来源，子代理只读自己一节 + 通用约定 + 接口约定（`:3`），完成后在 `changelogs/_audit-fix-report-<组名>.md` 回执（`:18`）。
- **未来的维护者 / AI agent**：靠条目里的 `文件:行号` 与函数名回溯实现，例如 `changelogs/CHANGELOG_v2.3.6.md:18` 的 `handle_process_failed`、`:27` 的两个新单测名。

**审计闭环的数据形状**

计划文件给出"项号 → 文件:行号 → 怎么改"，报告文件回"项号 → 位置 → 改法 → 验证"，两端项号一一对应（A 组 `:30`–`:47` 共 18 项，报告中以 `### A1 ·` 起逐节展开，`changelogs/_audit-fix-report-A.md:12`）。接口约定（`changelogs/_audit-fix-plan.md:22-26`）是跨组冻结面：命令名、事件名、字段名、签名变更都写死，前端组按此接线，任何组不得改名。

## Known Issues

1. **归档默认不在仓库里（设计结果，非缺陷）**。`changelogs/` 与 `release/` 均被 `.gitignore` 忽略，仅本地留存（`changelogs/CHANGELOG_v2.4.0.md:262` 明示 `.gitignore:7`；`changelogs/CHANGELOG_v2.3.8.md:32`、`changelogs/CHANGELOG_v2.3.7.md:25` / `:376` 记录本地保留口径）。后果：新克隆或换机后历史条目全部缺失，回溯只能靠维护者本机副本或 GitHub Release 正文（后者只覆盖 release notes，不含根因与验证细节）。

2. **行号口径在计划与报告之间反转，跨文件对读会错位**。`changelogs/_audit-fix-plan.md:32` 等处的行号写于修复前（原文常见"现为 :52-54""约 :42-60"），而 `changelogs/_audit-fix-report-A.md:3` 明确"所有行号为修复后当前代码位置"。同一项在两份文件里的行号必然不同，不能互相校验。

3. **前向引用断链**。`changelogs/_audit-fix-plan.md:47` 要求在工作代码注释里指向 `changelogs/CHANGELOG_v2.4.2.md`「设计决策与评估」节，而该文件在本次归档中尚不存在——归档只到 `CHANGELOG_v2.4.1.md`（`:3` 仍标"开发中"）。注释一旦落地即指向缺失文件。

4. **单文件内格式不统一，两种条目体例并存**。`changelogs/CHANGELOG_v2.4.0.md` 前半为 `### 分类` 下的 `- **日期 标题**` 列表（`:5`–`:268`），后半改为提交式段落 `## YYYY-MM-DD · 标题（feat/fix/ui）` + 需求/实现/验证子项（`:275` 起，典型 `:279`–`:282`、`:288`–`:290`）；两者行内结构（是否含"验证"子节、是否用 `###`）完全不同，机械解析会漏条目。

5. **同名分类节重复出现**。`changelogs/CHANGELOG_v2.3.7.md` 中 `### 缺陷修复` 出现两次（`:683` 与 `:872`），中间隔着 `### 前端性能优化`（`:587`）与 `### 文档`（`:608`）；按标题聚合会覆盖先出现的那一段。

6. **"追加"段与主段结构割裂**。`changelogs/CHANGELOG_v2.3.8.md` 主段用 `## v2.3.8` + `### 分类`，四段追加改用 `# 追加（第二批）` + `## 行为调整` / `## 验证数据`（`:50`、`:54`、`:67`、`:76`、`:92`、`:96`），标题层级整体上移一级，同文件内 `#` 级标题出现多次。

7. **版本封版状态在文件内无标记**。`changelogs/CHANGELOG_v2.4.0.md:3` 与 `changelogs/CHANGELOG_v2.4.1.md:3` 都写"（开发中）"，但对应的 `release/RELEASE_NOTES_v2.4.0.md`、`release/RELEASE_NOTES_v2.4.1.md` 已存在且含正式版本号；v2.3.8 / v2.3.9 则带"（2026-09-20 发布）"后缀（`changelogs/CHANGELOG_v2.3.8.md:3`、`changelogs/CHANGELOG_v2.3.9.md:3`）。是否已发布只能靠标题后缀人眼判断，且规则本身不统一。

8. **已终止方向被保留在归档中**。`changelogs/CHANGELOG_v2.4.1.md:34` 记录了 iOS 端 M0 骨架落地（`:36`，含 `ios/` 三目录与 GitHub Actions 流水线），`:42`/`:44` 紧接着记录移除全部 iOS 文件与本地分支；`release/RELEASE_NOTES_v2.4.1.md:25` 才向用户交代"8 轮 CI 攻坚未能打通构建"。归档保留了完整失败轨迹，但条目与发行说明的结论之间存在时间差，仅读 changelog 会误以为 iOS 仍在推进。

9. **跨目录引用靠手工维护，路径易漂移**。条目大量引用 `.codewiki/learnings/*`、`.codewiki/decisions/*` 作为根因依据（如 `changelogs/CHANGELOG_v2.3.7.md:66` 指向 `learnings/input-time-wrapper-w-full`、`:112` 指向 `learnings/nonblocking-connect-einprogress-not-wouldblock`、`changelogs/CHANGELOG_v2.3.8.md:32` 指向 `decisions/changelog-per-version-files`）。这些文章由 codewiki 流水线生成、标题随时可能改写，changelog 内的引用没有校验机制。

10. **校验和文件只覆盖单一资产**。`release/Wxxy-CampusLogin_2.4.1_x64-setup.exe.sha256:1` 只对 Windows 安装包，APK 的完整性依赖 GitHub 自动 digest（`release/RELEASE_NOTES_v2.3.3.md:48` 说明"GitHub 自动提供 digest 作为应用内更新校验值"）；镜像渠道下的 APK 校验因此不在本地归档内留痕。
