## Overview

`target-tmp/node-compile-cache/` 是 Node.js 运行时落盘的**编译缓存目录**，不属于项目源码。本仓库当前只有一代缓存：`target-tmp/node-compile-cache/v24.19.0-x64-cf738c9d/`，内含 1684 个无扩展名文件，实测合计 7,142,040 字节（`du` 因 Windows 小文件簇开销计为 11 MB）。每个文件首 4 字节均为 `b2dbdf8a`（V8 code cache 魔数），文件体是 V8 编译产物的二进制快照，因此本篇不做源码级解读：流水线指令里形如 `N| ` 的前缀是二进制转储的行偏移，不是源码行号。

目录名三段式 `v24.19.0-x64-cf738c9d` 的前两段与本机实测 `node -v` 的 `v24.19.0` 及 x64 架构一致，第三段是配置指纹；文件名统一为 8 位十六进制哈希。机制上，当 Node 运行时以 `NODE_COMPILE_CACHE` 指向该目录时，加载每个 `.js` 模块会把 V8 生成的字节码写入 `hash(源路径)` 文件，下次启动直接反序列化、跳过解析与编译，从而缩短 `vite` / `npm` 这类工具的冷启动时间。

该目录被 `.gitignore` 第 48 行的 `target-tmp/` 排除在版本控制外，同段落注释写明它是"会话临时产物(截图预览/构建实验)"。对全仓 `.ps1` / `.json` / `.md` / `.yml` 检索 `NODE_COMPILE_CACHE` 与 `target-tmp` 均无命中：仓库内既没有生成它的脚本，也没有清理它的脚本，缓存来自外部 Node 运行时环境，删除后按需重建。

本篇 `source_files` 列出本批次分配的 200 个缓存文件；目录内实际文件总数为 1684。

对全部 1684 个文件做 ASCII 串提取，内嵌的 `node_modules` 源路径按顶层段统计命中次数：`vite` 73、`@vitejs` 61、`.vite-temp` 59、`rollup` 8、`chalk` 4、`fdir` 3、`@rolldown` 2、`tinyglobby` 2、`postcss` 2。路径形态显示这些条目多数来自 pnpm 布局，例如 `.pnpm/@vitejs+plugin-react@4.7.0_vite@6.4.3_jiti@1.21.7_/node_modules/@vitejs/plugin-react/dist/index.js`、`.pnpm/sucrase@3.35.1/node_modules/sucrase/dist/transformers/ReactHotLoaderTransformer.js`、`.pnpm/tailwindcss@3.4.19/node_modules/tailwindcss/lib/util/defaults.js`、`.pnpm/autoprefixer@10.6.1_postcss@8.5.28/node_modules/autoprefixer/lib/hacks/align-content.js`、`.pnpm/picomatch@2.3.2/node_modules/picomatch/lib/parse.js`。对应的是前端构建链上的转译器、CSS 工具链与 glob 解析器。

### Vite 配置快照

`target-tmp/node-compile-cache/v24.19.0-x64-cf738c9d/01c92fc4` 内嵌源路径指向 `tauri-app/frontend/node_modules/.vite-temp/vite.config.ts` —— Vite 在加载配置前会先把它转译到 `.vite-temp` 目录，该转译结果的字节码即落在此缓存文件中。同一文件还内嵌 `@vitejs/plugin-react` 的 `dist/index.js` 路径。

### Node 全局 npm CLI

一批文件内嵌 `C:\Program Files\nodejs\node_modules\npm\lib\` 下的路径，例如 `lib\cli\entry.js`、`lib\commands\install.js`、`lib\utils\format.js`，以及嵌套依赖 `@npmcli/arborist/lib/arborist/reify.js`（见上文 `000a1de6`）、`@sigstore/sign/dist/util/oidc.js`、`@tufjs/models/dist/index.js`。也就是说，同一份缓存既覆盖项目本地依赖，也覆盖执行 `npm` 命令时加载的全局 CLI 模块。

### 命名与布局约定

- 一级：`target-tmp/node-compile-cache/`
- 二级：`<node 版本>-<arch>-<配置指纹>/`，当前仅 `v24.19.0-x64-cf738c9d`
- 三级：8 位十六进制哈希文件，无扩展名，与源路径一一对应
- 无索引文件、无清单文件，条目之间无显式引用关系

## Architecture

```text
构建/运行命令 (npm run dev / npm install / vite)
        |
        v
Node v24.19.0 运行时
        |  NODE_COMPILE_CACHE 指向 target-tmp/node-compile-cache
        |  加载项目依赖与全局 npm CLI 的 .js / .ts 源
        v
   V8 解析 + 编译
        |
        +-- 未命中 --> 编译后写入 hash(源路径) 文件
        |
        +-- 命中   --> 反序列化字节码, 跳过解析与编译
                            |
                            v
        target-tmp/node-compile-cache/v24.19.0-x64-cf738c9d/  (1684 个快照)
                            |
        失效条件: Node 版本变化(目录段) / 依赖路径变化(hash 变) / 源文件内容变化
```

## Data Flow

1. 命令启动 Node 进程，运行时读取 `NODE_COMPILE_CACHE`，定位到 `target-tmp/node-compile-cache`。
2. 拼出 `<node 版本>-<arch>-<配置指纹>` 子目录；版本段来自当前运行时（实测 `v24.19.0`），换 Node 版本即落到另一个子目录。
3. 每个被加载的 JS/TS 模块按源路径哈希查找既有文件：命中就直接使用已编译字节码；未命中则正常编译并写回新文件。
4. 因此缓存是"构建当时依赖树"的快照。当前 `tauri-app/frontend/node_modules` 已不存在缓存中引用的 `.pnpm/sucrase@3.35.1`、`.pnpm/tailwindcss@3.4.19` 与 `.vite-temp/` 目录，说明依赖重装或版本漂移后这些条目已无对应源、不会再命中，只能等新条目写入。
5. 清理路径：删除整个 `target-tmp/` 即回到无缓存状态，Node 下次运行重新写入，`git status` 不受影响（第 48 行已忽略）。

## Known Issues

1. **二进制不可审阅**：文件是 V8 字节码快照，没有可读源码语义；转储行号不是源码行号，任何"某函数在第 N 行"的解读都不可复现。
2. **与 [[tauri-node-compile-cache]] 重复记录同一目录**：两篇覆盖同一批文件，后者把转储行号当作源码行号引用（如 `line 4`），并回链 `vite-config`、`postcss-config` 等本仓并不存在的模块；核对时以本目录实测为准。
3. **依赖漂移造成悬空条目**：实测缓存引用的 `.pnpm/sucrase@3.35.1`、`.pnpm/tailwindcss@3.4.19`、`.vite-temp/` 已不在当前 `tauri-app/frontend/node_modules` 中，这些条目永不再命中，只白占体积。
4. **版本升级不回收旧目录**：Node 只写当前版本前缀的二级目录，切换 Node 版本后旧目录（当前仅有 `v24.19.0-x64-cf738c9d` 一代）会残留，需手工删除 `target-tmp/`。
5. **体积被小文件开销放大**：1684 个文件实际字节 7.1 MB，`du` 计 11 MB；虽已 ignore，仍会出现在任何按磁盘扫描的备份或打包动作里。
6. **不可复现**：仓库无脚本设置 `NODE_COMPILE_CACHE`，该目录只存在于曾开启缓存的机器上，不能当作构建输入，也不能用于对比构建性能。
